# 프로젝트 시작 전 꼭 해야 할 설계 3단계

## 1. 유저 플로우 / 시퀀스 설계
**❓무엇인가**
- 사용자가 어떤 기능을 어떤 순서로 사용할지를 정하는 것이다.
    - ex) 로그인 -> 상품 조회 -> 장바구니 담기 -> 주문 -> 주문내역 확인

**🤔 왜 필요한가**
- 사용자의 실제 사용 흐름을 기준으로 **기능 요구사항**을 도출할 수 있다.
- 어떤 API가 필요한지, 어떤 데이터가 오가야 하는지 명확해진다.
- **기획과 설계의 출발점**이자, 기능 개발의 기준선이 된다.

## 2. ERD 설계(데이터 모델링)
**❓무엇인가**
- 서비스에서 필요한 **데이터 구조(Entity)와 관계(Relation)** 를 정의하는 작업이다.
    - ex) User, Product, Cart, Order 등의 테이블과 관계를 정의

**🤔 왜 필요한가**
- 기능을 구현하기 전에 **무엇을 저장하고 어떻게 연결할지** 미리 결정해야 코드가 정리된다.
- DB 구조가 명확하지 않으면, 개발 도중에 꼬이고 변경된다.
- 복잡한 기능(주문, 장바구니, 리뷰 등)을 제대로 다루기 위해 **정확한 데이터 모델**은 필수이다.

## 3. 아키텍처 설계 / 폴더 구조 설계
**❓무엇인가**
- 프로젝트의 **전체 구조, 계층(Controller, Service, Reposioty 등), 코드의 역할 분리**를 설계하는 것이다.
- 도메인별로 패키지를 나누고 공통 기능은 global/config 등으로 분리한다.

**🤔 왜 필요한가**
- 혼자 개발하더라도 **규칙 있게 관리하지 않으면 금방 난장판**이 된다.
- 역할을 명확히 나누면 기능 확장/유지보수가 쉬워진다.
- JWT, 인증, 예외처리 같은 보안/전역 설정도 따로 정리해서 **재사용** 가능
- MVC 패턴에 기반한 깔끔한 설계를 통해 **협업**할 때 유용하다.

## MSA
**❓무엇인가**
- **MSA(Microservice Architecture)** 는 하나의 애플리케이션을 **작은 서비스 단위로 나누어 개발 및 배포하는 아키텍처 스타일**이다.
- 각 서비스는 **독립적으로 동작**하며, 필요한 경우 서로 **API를 통해 통신**한다.

### ✅ [좋은 예] - 도메인/계층이 명확하게 분리된 구조
- 대규모 서비스 운영 중일 때
- 사용자 수가 많고, 트래픽이 특정 기능에 집중될 때
- 서비스 간 기능이 명확하게 분리되어 있을 때
- 팀이 여러개로 나뉘어 분산 개발이 필요한 경우
- 규모가 클 때 사용

```java
src/main/java/com/example/coupangclone
├── config                 # 설정 파일 (Security 등)
├── global                 # 공통 기능 (예외 처리, 응답 포맷 등)
├── jwt                    # JWT 관련 클래스
├── user                   # 유저 도메인
│   ├── controller
│   ├── service
│   ├── repository
│   └── domain             # Entity 클래스
├── product                # 상품 도메인
│   ├── controller
│   ├── service
│   ├── repository
│   └── domain
├── cart                   # 장바구니 도메인
│   ├── controller
│   ├── service
│   ├── repository
│   └── domain
├── order                  # 주문 도메인
│   ├── controller
│   ├── service
│   ├── repository
│   └── domain
└── MallApplication.java   # 메인 클래스
```
<br/>

✔️ **이 구조의 장점**
- **도메인 단위로 폴더 정리**되어 있어 기능별로 파악이 쉽다.
- 계층 분리(controller/service/repository/domain)이 잘 되어 있어서 **확장성과 유지보수에 유리하다**
- 보안, 설정, 공통 기능도 **분리 관리 가능하다.** -> 재사용성과 가독성 향상

<br/>

### ❌ [안좋은 예] - 파일이 뒤섞이고 역할이 불분명한 구조
- 기능이 단순하고, 도메인 간 연계가 강한 경우
- MVP 단계에서 아직 검증되지 않은 서비스를 무리하게 분리한 경우
- 규모가 작을 때 사용

❗이런 상황에선 MSA가 오히려 개발 속도를 떨어뜨리고 복잡도만 증가시킬 수 있다.

```java
src/main/java/com/example/coupangclone
├── controller
│   ├── UserController.java
│   ├── ProductController.java
│   ├── CartController.java
│   └── OrderController.java
├── service
│   ├── UserService.java
│   ├── ProductService.java
│   ├── CartService.java
│   └── OrderService.java
├── repository
│   ├── UserRepository.java
│   ├── ProductRepository.java
│   ├── CartRepository.java
│   └── OrderRepository.java
├── domain
│   ├── User.java
│   ├── Product.java
│   ├── Cart.java
│   └── Order.java
├── SecurityConfig.java
├── JwtProvider.java
├── JwtAuthenticationFilter.java
├── GlobalExceptionHandler.java
└── MallApplication.java
```
<br/>

✖️ **이 구조의 문제점**
- 모든 도메인이 **한 폴더에 섞여 있어서 규모가 커지면 파일 찾기 어렵고 복잡해진다.**
- 공통 기능이 구조적으로 분리되어있지 않다.
- 도메인 간의 **경계가 흐려지고, 유지보수가 어렵다.**

### MSA 정리
| 설계 단계 | MSA 구조 | 잘못된 Monolithic 구조  |
| --- | --- | --- |
| 도메인 분리 | O(user, product 등 분리) | X(모든 클래스가 한곳에 모임임) |
| 계층 분리 | O(도메인 별로 잘 분리) | O(하지만 도메인별 아님) |
| 공통 기능 위치 | 명확하게 global/config로 분리 | 파일마다 위치가 불명확 |
| 확장/유지보수 | 매우 쉬움 | 커지면 감당 불가 |

### 📍결론 및 느낀점
이번 설계를 정리하면서 느낀 건, **코딩을 빨리 시작하고 싶을수록 오히려 설계를 더 꼼꼼히 해야 한다**는 점이다.

예전에 유저 플로우, ERD, 아키텍처를 제대로 만들지 않고 개발을 시작했을 때, 중간에 방향이 흔들리고 구조가 어지러워져서 결국 다시 손보는 일이 많았다. 그 경험을 통해 설계가 얼마나 중요한지를 직접 체감할 수 있었다.

그 당시엔 잘못된 Monolithic 구조로 개발을 했었는데, 기능이 늘어날수록 파일을 찾는 데 시간이 오래 걸리고, 전체 구조가 어지럽게 느껴져서 개발 자체에 피로감이 쌓였다. 그래서 지금은 **파일을 어디에 넣고, 어떤 기능이 어디로 연결되는지 명확한 구조**가 얼마나 중요한지를 느끼고 있다.

MSA 구조를 공부하면서 가장 크게 와닿은 건, **좋은 설계는 프로젝트 규모와 상관없이 '읽기 쉬운 코드'를 만드는 데 핵심적인 역할을 한다는 것이다.**

결국 내가 만든 기능이 **어떤 구조 안에서 어떻게 동작하는지를 미리 고민하고 만드는 것**, 그게 바로 **‘미래의 나’** 와 협업하는 일이라는 걸 이번 정리를 통해 다시 한 번 실감하게 되었다. 그리고 그런 설계는 **다른 개발자도 코드를 빠르게 이해하고, 쉽게 협업할 수 있는 기반**이 된다는 것도 느꼈다.
