# JWT(Json Web Token)
JWT는 인증에 자주 쓰이는 **토큰 기반 인증 방식**중 하나다.<br/>
JSON 형식의 정보를 암호화해서 클라언트에 전달하고, 클라이언트가 이 토큰을 가지고 있으면 매번 로그인하지 않아도 된다.

## JWT 구조
```
HEADER.PAYLOAD.SIGNATUE
```

- **Header** : 어떤 알고리즘(alg)으로 서명했는지, 토큰 타입(typ)이 뭔지 알려준다.
- **Payload** : 유저 정보, 권한, 만료 시간 같은 내용들(claim 이라고 부름)을 알려준다.
- **Signatue** : 이 토큰이 위조되지 않았다는 걸 보장하는 서명이다.

> 💡 Header + Payload 를 secret key로 서명한 값이 Signature 이다.

## 🔐 JWT Secret key 란

JWT의 Signature는 서버가 가진 **Secret Key**로 만들어진다.  
클라이언트가 보내는 JWT를 서버가 검증할 수 있는 이유는, **같은 키로 Signature를 다시 계산해 비교하기 때문.**

- 서버는 이 Secret Key로 JWT를 **서명(Sign)**
- 클라이언트는 이 토큰을 API 호출에 사용
- 서버는 **같은 Key로 검증(Verify)**

> ❗️ **Secret key가 유출되면 토큰 위조가 가능해지기 때문에 절대 외부에 노출되면 안된다.**

### JWT Secret Key 생성 방법법

터미널에 아래 명령어를 실행해 안전하고 복잡한 키를 생성할 수 있다다.

```bash
openssl rand -base64 64
```

생성된 키는 보통 application.yml 등에 저장하고 코드에선 `@Value`로 주입한다.

### [추가] jwt.io에서 Invalid Signature가 뜨는 이유
JWT를 발급하고 jwt.io에서 직접 확인해보면 종종 `Invalid Signature` 라는 메시지가 뜬다.<br/>
이 경우 대부분 다음 두 가지 중 하나다:

1. Base64 인코딩된 Secret Key가 다르거나 올바르지 않음
2. JWT 생성 시 사용한 서명 알고리즘 또는 시크릿 키 방식이 다름

>✅ jwt.io는 입력한 Secret Key를 가지고 Signature를 다시 계산해서 비교하는데,
Spring 프로젝트에서 사용하는 Secret Key가 정확히 Base64로 인코딩된 값이어야 검증에 성공한다.

application.yml에 저장한 키를를 복호화하거나 공백이 있으면 jwt.io에선 "Invalid Signature" 라고 뜰 수 있다. 하지만 실제 인증 흐름은 jwt.io가 아닌 서버 내부의 JwtProvider에서 이루어지므로, 여기서 통과되면 문제되지 않는다.

**단, 절대로 Secret Key를 브라우저나 외부 도구에 입력하면 안된다!**

jwt.io는 **디버깅/확인용 도구** 일 뿐이다.

## 🔄️ JWT 동작 방식
1. 클라이언트가 로그인 → 서버에서 JWT 발급
2. 클라이언트는 이 토큰을 Authorization 헤더에 포함하여 API 요청
3. 서버는 JWT의 유효성 검사 후 인증된 사용자로 판단
4. 세션/쿠키 없이도 인증 상태 유지 가능 (Stateless)

## ❓왜 JWT를 사용할까
- **Stateless 인증**
    - 세션 저장소 없이 인증 상태 유지 가능 -> 서버 확장에 유리하다.
- **데이터를 직접 담을 수 있음 (claim)**
    - payload에 원하는 값을 담아서 별도 조회 없이 인증/인가 처리 가능하다.
- **요청 속도 빠름**
    - 매 요청마다 토큰만 검증하면 되니까, DB 조회 없이 빠르게 인증 가능하다.

## 💫 JWT의 한계점
- 서버에서 토큰 무효화 불가
    - 발급된 토큰은 클라이언트가 갖고 있으므로 서버에서 강제로 만료시킬 수 없다.
    - 해결법 : AccessToken 만료시간 짧게 설정 + RefreshToken 도입
- 탈취 시 위험
    - 노출된 토큰은 누구든 사용 가능하므로 HTTPS 강제 + 만료 주기 짧게 해야한다,
- Payload는 암호화되지 않음
    - Base64 인코딩이므로 민감 정보 저장은 절대 금지

## ☑️ Access Token vs Refresh Token
JWT 기반 인증을 실제 서비스에 적용할 때는 일반적으로 AccessToken + RefreshToken 조합을 사용한다.

| 구분 | Access Token | Refresh Token | 
| --- | --- | --- |
| 목적 | 인가(Authorization) | Access Token 재발급 |
| 수명 | 짧음(ex. 15분) | 김(ex. 7일~30일) |
| 저장 위치 | 클라이언트(LocalStorage, 메모리) | 보통 HttpOnly 쿠키 |
| 노출 위험 | 높음 -> 탈취되면 위험 | 낮음(HttpOnly 설정 시 XSS 방어) |
| 만료 시 처리 | Refresh Token으로 재발급 | 로그인 다시 해야 함 |

### ❓왜 둘 다 써야할까?
- Access Token을 짧게 만들어서 노출되어도 피해를 줄 수 있다.
- Refresh Token은 로그인 세션처럼 사용 -> Access Token이 만료되면 **서버에서 Refresh Token 확인 후 새로운 Access Token 재발급**

이 구조를 통해 사용자는 재로그인 없이도 계속 서비스를 사용할 수 있고, 서버는 보안을 유지할 수 있다.

> Access Token은 사용자 인증을 위한 것<br/>
> Refresh Token은 사용자 경험과 보안을 동시에 지키기 위한 보조 토큰

### ⚠️ 주의할 점
- Refresh Token이 탈취되면 장기 로그인 유지가 가능하므로 훨씬 더 위험하다
    - **HttpOnly + Secure** 설정으로 방지
- Refresh Token을 DB 또는 Redis에 저장해서, **재발급 요청 시 서버에서 유효성 체크하는 방식을 권장**

### 🍪 HttpOnly와 Secure 란?
### 1. HttpOnly
자바스크립트에서 쿠키에 접근할 수 없도록 막는 설정
- HttpOnly가 설정된 쿠키는 JavaScript로 접근 불가
- 즉, **XSS 공격**(악성 스크립트를 통한 쿠키 탈취)으로부터 보호됨

### 2. Secure
HTTPS(보안 연결)를 통해서만 쿠키를 전송하도록 제한하는 설정

- Secure 옵션이 설정된 쿠키는 **HTTPS 연결일 때만 서버로 전송됨**
- HTTP 연결일 땐 아예 쿠키가 전송되지 않아서 **중간자 공격(MITM)** 방지에 유리


### 예시
```java
ResponseCookie cookie = ResponseCookie.from("refreshToken", token)
        .httpOnly(true)
        .secure(true)
        .path("/")
        .maxAge(Duration.ofDays(7))
        .build();

response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());
```

### 🔥다음 목표
오늘은 Access Token 기반 로그인까지만 구현했지만, Refresh Token 기반 자동 로그인/재발급 시스템도 도입해보고 싶다.
- Refresh Token을 **HttpOnly + Secure 쿠키에 저장**
- 서버에 Refresh Token을 **DB 또는 Redis에 저장해 유효성 체크**
- Access Token 만료 시 **Refresh Token으로 자동 재발급 로직 구현**

이 과정을 구현하면서 보다 실전적인 인증 흐름을 완성해보고 싶다.

JWT는 단순한 토큰이 아니라, **보안과 구조 설계까지 함께 고려해야 하는 인증 시스템** 이라는 걸 실감했다.
