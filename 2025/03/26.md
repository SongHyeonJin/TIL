# Kafka란?

**Apache Kafka**는 고성능 데이터 파이프라인, 스트리밍 분석, 데이터 통합 및 미션 크리티컬 애플리케이션을 위해 설계된 **오픈 소스 분산형 이벤트 스트리밍 플랫폼**이다.

> **📌 이벤트 스트리밍이란?**  
> 이벤트를 실시간으로 생성, 저장, 처리, 전파하는 아키텍처 패턴  
> → 마치 **인체의 중추 신경계**처럼, 시스템 간 데이터 흐름을 빠르고 유연하게 연결해준다.

---

## 분산형 이벤트 스트리밍 플랫폼

- **분산형**: 여러 서버나 노드에 데이터와 처리를 분산하여 **높은 가용성**과 **수평 확장성**을 제공함.
- **이벤트 스트리밍 플랫폼**: 이벤트가 발생할 때마다 그 정보를 **지속적으로 수집하고 전송하며 처리**하는 시스템.

### 이벤트 스트리밍 플랫폼이란?

이벤트 스트리밍 플랫폼은 **시스템에서 발생하는 모든 이벤트(데이터 변화, 사용자 활동 등)를 실시간으로 처리하고 전파**할 수 있도록 해주는 인프라다. 단순히 메시지를 전달하는 것이 아니라, 이벤트를 **기록하고**, **구독자에게 배포하고**, **필요시 다시 처리까지** 할 수 있는 구조를 갖추고 있다.

---

### Kafka는 이 모든 기능을 하나로 통합하여 제공한다.

Kafka는 다음의 3가지 핵심 기능을 통해 **end-to-end 이벤트 스트리밍 아키텍처**를 구현할 수 있다.

1. **이벤트 발행 및 구독 (Publish & Subscribe)**  
   - Producer가 이벤트를 Kafka에 발행하고  
   - Consumer가 Topic을 구독하여 실시간으로 이벤트를 수신

2. **이벤트 저장 (Durable Storage)**  
   - 발행된 이벤트는 Kafka의 Broker에 있는 Topic-Partition 구조에 **내구성 있게 저장**됨  
   - 설정된 보존 기간 동안 이벤트를 **재처리(replay)** 가능

3. **이벤트 처리 (Processing)**  
   - Kafka Streams, ksqlDB 등을 통해 이벤트 스트림을 **실시간으로 분석/처리**할 수 있음  
   - 또는 Spark, Flink, Spring Cloud Stream 등 외부 처리 시스템과 연동 가능

이러한 구조 덕분에 Kafka는 단순한 메시지 큐가 아닌, **데이터의 흐름을 중심으로 한 아키텍처**를 구성할 수 있게 해주는 강력한 플랫폼이다.

## Kafka 구성 요소

### Topic, Partition, Offset

<img src="https://github.com/user-attachments/assets/52d6f9d2-17cd-4c80-ae65-c06fbc7c7a86">

<br/>

- **Topic** : 메시지를 구분하는 단위
    - 이벤트의 종류별로 구분된 채널로, Producer는 특정 Topic에 메시지를 발행하고 Consumer는 구독한다.
    - ex) 주문 이벤트는 `order-topic`, 결제 이벤트는 `pay-topic` 등으로 구분 가능

- **Partition** : 메시지를 저장하는 물리적인 파일
    - 하나의 Topic은 한 개 이상의 Partition으로 구성된다.
    - Kafka의 병렬 처리와 확장성을 가능하게 한다.
    - 각 Partition은 메시지의 순서를 보장하며, 여러 Consumer가 병렬로 데이터를 처리할 수 있도록 돕는다.
- **Offset** : Partition 내에 고유한 순번을 나타내는 값
    - Producer가 넣은 메시지는 Partition의 맨 뒤에 추가
    - Kafka는 메시지를 삭제하지 않고 저장하며, Consumer는 자신이 마지막으로 읽은 메시지의 Offset을 기억함

### Producer, Consumer & Consumer Group

<img src="https://github.com/user-attachments/assets/ba8f01f3-b2df-43c4-b07c-2fd972d36611" />

<br/>

- **Producer** : 메시지를 발행하여 생산하는 주체 (writer)
    - Kafka로 데이터를 보내는 역할을 한다.
    - 메시지를 특정 Topic에 전송하고, 메시지 키에 따라 Partition을 지정할 수 있다.
    - 이 키 덕분에 동일한 키를 가진 메시지는 항상 같은 Partition에 저장되어 순서가 유지된다.

- **Consumer & Consumer Group** : 메시지를 구독하여 소비하는 주체 (reader), consumer의 모임
    - Consumer는 Kafka에서 메시지를 읽어오는 주체이다.
    - 여러 Consumer가 Topic을 동시에 처리할 수 있게 하려면, 이들을 하나의 Consumer Group으로 구성한다.
    - Consumer Group 내부에서는 Partition이 Consumer 간에 분배되어 병렬 처리가 가능해진다.

    > 💡 _이때 중요한 규칙이 있다._ <br/> 
    하나의 Partition은 동일한 Consumer Group 내에서 단 하나의 Consumer에게만 할당될 수 있다. 즉, 하나의 Partition은 동시에 여러 Consumer가 읽을 수 없고, 1개의 Consumer만이 해당 Partition을 소비한다. 이 때문에 일반적으로는 Partition 수 == Consumer 수가 가장 이상적인 구조이다. 단, 하나의 Consumer가 여러 Partition을 담당할 수 있으므로, Consumer와 Topic 간에는 1:N 관계도 가능하다.

### Broker, Zookeeper

- **Broker** : Producer와 Consumer를 연결하는 중재자

<br/>

<div align="center">
  <img src="https://github.com/user-attachments/assets/68558da3-a89d-4e72-9cf6-d1af3cae654f" width="60%" />
</div>

<br/>

Broker는 Kafka 시스템 내의 개별 서버 혹은 노드를 뜻하며 Producer와 Consumer를 연결하는 중재자 역할을 한다. Partition들은 Broker에 저장된다. Producer가 데이터를 생성하여 Kafka의 특정 Topic에 전송하며 Broker는 메시지를 받아 해당 Topic의 적절한 Partition에 저장한다.

Consumer는 Kafka Topic의 데이터를 읽기 위해 Broker에 접속한다. Broker는 Consumer의 요청에 따라 메시지를 전송하며 Consumer가 어디까지 데이터를 읽었는지 Offset(위치)을 관리한다.

Kafka의 Broker는 다른 메시지큐(RabbitMQ, ActiveMQ)와는 다른 차이점이 있다.
일반적인 메시지 큐들은 메시지를 메모리에 저장하지만 Broker는 데이터(메시지)를 로컬 스토리지에 파일로 저장한다. 이로 인해 Kafka를 재시작해도 메시지 유실 우려가 적다.

또한 일반적인 메시지 큐는 메시지를 중재자가 push 방식으로 소비자에게 전달하지만 Kafka의 Broker는 Consumer가 처리할 수 있는 만큼 pull하는 구조이다. Consumer가 자신의 능력만큼 데이터를 가져오므로 최적의 성능을 낼 수 있다.


- **Zookeeper** : 분산 코디네이션 서비스

<br/>

<img src="https://github.com/user-attachments/assets/801e36e7-1f82-4f87-b341-cf8bf7e57775" />

<br/>

Kafka에서 Zookeeper는 클러스터의 상태를 관리하고 조율하는 중요한 역할을 한다. Zookeeper는 Kafka의 Broker 정보, Topic 및 Partition 정보 등 메타데이터를 저장하고, 각 Broker들의 상태를 모니터링하며 관리하는 기능을 수행한다.

Kafka를 실행할 때는 Zookeeper가 반드시 먼저 실행되어야 하며, Kafka는 이를 통해 클러스터의 안정성을 유지한다. 이러한 구조는 Kafka 2.x 버전까지는 필수였기 때문에, Kafka를 운영하려면 항상 Zookeeper를 함께 구성해야 했다.

하지만 Kafka 3.x 버전부터는 Zookeeper에 대한 의존도를 줄이기 위해, Zookeeper 없이도 동작 가능한 KRaft(Kafka Raft) 모드가 도입되었다. KRaft는 Kafka 내부에 메타데이터 관리 기능을 내장하여, 보다 단순하고 효율적인 클러스터 구성이 가능하도록 설계되었다.

### Replication 

Topic의 복제

- 각 Partition에는 하나의 Leader Replica가 존재하고, 나머지는 Follower Replica이다.
- 모든 Read/Write 작업은 Leader에서만 처리되며, Follower는 이를 따라가며 동기화한다.
- 만약 Leader에 장애가 발생하면, ISR(In-Sync Replica) 중 하나가 새로운 Leader로 승격된다.

Kafka는 **고가용성(HA)** 을 위해 메시지를 복제하는 **Replication** 기능을 제공한다.
하나의 Partition은 복제본(Replica)을 가질 수 있으며, 이들은 서로 다른 Broker에 분산되어 저장된다.

이를 통해 Kafka는 Broker 장애 시에도 데이터 유실 없이 안정적으로 메시지를 제공할 수 있다.
복제 개수는 Topic 생성 시 `replication.factor` 설정으로 지정할 수 있으며, 일반적으로 2 또는 3이 권장된다.

## 👍🏻 Kafka 장점
### 고성능
- 대용량 처리에 최적화 (고처리량, 낮은 지연 시간)
- Partition 기반 병렬 처리와 수평 확장 용이

### 고가용성
- Replication으로 장애 대응 가능
- Offset 기반 재처리 지원, 안정적인 메시지 저장

### 연동성과 확장성
- 다양한 소비 방식과 외부 시스템 연동 (Spark, Flink 등)
- 클라우드, 온프렘 등 다양한 환경에서 유연한 배포
- Kafka는 다양한 외부 시스템과 쉽게 연동되어, 실시간 데이터 파이프라인 구성에 강력한 유연성을 제공

### 안정적인 저장
- 디스크 기반 저장으로 메시지 유실 방지
- 장기 저장 및 재처리, 감사 로그 용도 가능


## 🔄️ Kafka 2.x vs 3.x 비교

| 항목 | Kafka 2.x | Kafka 3.x |
| ---| --- | --- |
| **Zookeeper 의존성** | 필수 | 기본적으로 존재, 하지만 **Zookeeper 없는 구조(KRaft)** 지원 시작 |
| **KRaft 모드** | 지원 안함 | 실험적 도입 -> 3.3 이상에서 안정화 진행 중 |
| **메타데이터 관리** | Zookeeper에서 처리 | KRaft 모드에서는 Kafka 내부에서 처리 |
| **설치 및 운영 복잡도** | Zookeeper 따로 설치 및 관리 필요 | KRaft 사용 시 Zookeeper 생략 가능 |
| **클러스터 구성 방식** | Zookeeper 기반 브로커 관리 | KRaft 기반의 컨트롤러 노드 도입(기본적으로 1~3개) |
| **기능 업데이트** | 기본적인 기능은 완성도 높음 | 새로운 기능들 다수 도입 중(KRaft, 새로운 Consumer group protcol 등) |
| **최신 커넥터 및 툴 호환성성** | 구버전 일부 미지원 | 최신 버전과의 호환성 보장(Flink, Debezium 등) |
| **운영 난이도** | 비교적 높음(Zookeeper 때문) | 낮아짐(Zookeeper 없이 구성 가능) |
| **API 변경** | 일부 메서드/옵견 deprecated | 많은 설정 옵션 및 API 개선(명확성 향상) |

### ❓KRaft 모드
KRaft모드는 Kafka가 **자체적으로 메타데이터를 관리**하고, **Zookeeper 없이 클러스터를 구성**할 수 있게 해주는 새로운 아키텍처이다.

- `metadata.log`라는 전용 internal topic을 통해 브로커 상태, 토픽, 파티션 정보를 관리
- Kafka 내부에서 **Raft consensus protocol**을 사용해서 클러스터 리더 선출, 복제 등을 수행
- Kafka의 **자급자족형 시스템으로 진화**하는 핵심 기반

### ✅ 주요 변화
- **KRaft 모드 도입(3.0~)**
    - Zookeeper 없는 kafka 클러스터 구성 가능
    - 단일 바이너리로 클러스터 실행 가능 (`process.roles=broker,controller`)
- **로그 디렉토리 자동 생성 옵션 추가**
    - `log.dirs` 경로가 없을 경우 자동으로 디렉토리 생성
- **API 및 설정 키 개선**
    - 일부 오래된 설정 키 deprecated
    - ex) `log.retention.hours` -> `log.retention.ms`
- **새로운 Consumer group protocol 실험적 도입 (3.2+)**
    - 기존보다 유연한 그룹 재조정 방식 제공 (Cooordinator 분산 처리 기반)

### ⚠️ 주의할 점
- **KRaft 모드는 기존 Zookeeper 기반 Kafka와 호환되지 않음**
- 2.x에서 3.x로 업그레이드 시, Zookeeper 기반을 유지하려면 **KRaft 사용 금지**
- **KRaft는 전환 과정에서 메타데이터 migration 필요**
